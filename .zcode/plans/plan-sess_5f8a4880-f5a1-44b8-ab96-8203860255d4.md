# Read → "Books | Audio" — Layout Blueprint

Design decisions (confirmed): **top segmented control** inside the Read tab, **estimated word timing** (upgrade later), **first-chapter-free** preview. Implementation is deferred — this is the blueprint the later work follows.

## 1. Read tab restructure (`mobile/src/screens/Reader.tsx`)

Add a segmented control ("Books | Audio") pinned at the top of the Read tab; the app keeps its 5-tab structure.

- **Books view** — exactly today's shelf: rails (Scriptures, Vedas, Stories…), Continue reading card. Untouched.
- **Audio view** — new posture in the same screen:
  - **Continue listening** card at top: book title, chapter/verse, thin progress bar, tap → resumes the player at the saved position.
  - **Rails of audio-capable books only** (reuse `RAIL_DEFS`, filtered to books with chant coverage > 0). Covers get a headphone badge and a "voiced X of Y verses" line, so partial coverage is honest.
  - Paid books show the same Plus badges/locks as the Books view — same entitlement data, one visual language.
  - Tapping a cover → chapter list (reuse `BookIndex`/`PagedBookIndex` pattern) → tapping a verse opens the player at that verse (`Listen` route `{bookKey, index, chapter}` — already exists).

## 2. Audiobook player (evolve `mobile/src/screens/Listen.tsx`)

Keep the `Listen` route; restructure the screen into the audiobook player:

- **Header**: book title, chapter picker sheet, close.
- **Mode selector chips: Verse | Meaning | Both** — only chips whose audio exists for this book are rendered (per your spec: both / only-meaning / only-verse). Persisted per book. Phase 1 ships with Verse enabled (chant audio exists); Meaning/Both activate once meaning narration is rendered.
- **Now-playing card**: the sounding verse large in Devanagari with **word-level karaoke highlight** (§3); meaning text shown below when the mode includes it (muted until its audio segment sounds).
- **Transport bar** (extend `ChantPlayer`): prev-verse / play-pause / next-verse, repeat verse/chapter, speed (0.75 / 1 / 1.25 / 1.5), **autoplay toggle** (off = stop after current verse).
- **Lock-screen / background playback = paid only**: `useChant` already sets `shouldPlayInBackground`; gate it — free tier pauses when the app backgrounds, entitled learners continue. Entitlement check comes from the learner API (server is the source of truth), never a client flag.
- Audio position persistence (`services/audioProgress.ts`, mirroring `readingProgress.ts`) powers Continue listening.

## 3. Word-level highlight (the "मा glowing" feature)

- New `wordAt()` in `mobile/src/recite/chantClock.ts`: within the sounding line's `[start_ms, end_ms]`, split into words (prefer `word_breakdown` words; fallback whitespace split), weight each by `aksharaCount()` (already in the file), interpolate elapsed time → active word. Same estimation pattern as the line fill bar and Guru viseme timing.
- `ChantList.tsx` `VerseCard`: render lines as word spans; the active word gets a **mild** treatment — soft gold background tint (~15% opacity) with a short Reanimated fade, not the bold line-gold. Line-level highlight stays as the coarse layer beneath.
- **Upgrade path built in**: `ChantLine` type gains optional `words?: {text, start_ms, end_ms}[]`; when the GPU pipeline later emits exact word timestamps, `wordAt()` prefers them and the UI needs no redesign. No audio re-render blocks launch.

## 4. Verse / Meaning / Both — audio data

- Verse audio = existing chant (`ChantInfo` on `Shloka`).
- Meaning narration = **new render pass** (`translation_hi`/`translation_en` → Sarvam TTS via the existing pre-render script pattern, e.g. `render_guide_audio.py`), stored per verse alongside chant, exposed as a meaning track in the API.
- "Both" interleaves per verse: verse audio → meaning audio → next verse (controlled by the player's queue, not by re-rendered combined files).
- Voice selection: deferred (structure supports one `voice` field per track already).

## 5. Selling books & free preview — reuse what exists

- The entire gate is already built and tested: `Entitlement` + `has_entitlement()` seam, `CanonText.tier`, `canon_access.py` **first-chapter-free** (first 5 verses for one-chapter books), `locked`/`preview`/`locked_after` in the API, Plus badges + `PlusSheet` in the app. No new preview logic needed.
- Still missing (later, owner-gated): payment SDK/store integration feeding `provision()` server-side, prices (DECISIONS.md P14), and turning on `CANON_PLUS_GATE` when buying works. Nothing in this layout blocks on it.

## Phasing when implementation starts

1. **Phase 1 — layout & player**: segmented control, Audio shelf + Continue listening, player restructure (mode selector with Verse live), autoplay + speed, estimated word karaoke, audio position persistence. Pure mobile work, ships on today's chant audio.
2. **Phase 2 — meaning audio**: Sarvam render pass for meaning tracks, Meaning + Both modes, word timestamps in the GPU pipeline output.
3. **Phase 3 — money**: store integration → `provision()`, background-audio entitlement gating live, voice selection.
